# Project-local booster lifecycle

Use the pinned catalog in `boosters.json`. The six core entries are checked during bootstrap. For later sections, use `LVR booster plan --section <S> --harness <harness>` before the section starts. Only install applicable conditional entries. Keep pending entries pending until the user confirms the relevant condition. Reference entries are read and credited as material for the section.

## Stage a missing skill

1. Check the harness's live list and the paths from `LVR booster check --name <id>`. Leave any existing skill, lock, link or configuration file in place. Load and use pre-existing skills through the harness when possible. They belong to the user. A copy in the user's home skill folder counts as present: `LVR booster check --journal` records its version and folder hash instead of staging a project copy.
2. Create a fresh project-local directory named `.lvr/booster-stage.<id>` with no links in its path. Initialise a temporary Git repository in that directory so the installer uses it as a project. Inside it, create a separate source checkout. Fetch the exact catalog SHA from the catalog repository over HTTPS and check it out detached. Verify `git rev-parse HEAD` in the source checkout against the catalog SHA before continuing.
3. From the staging project, run the chosen harness's command from the plan. Replace `./<pinned-checkout>` with the path to the checked-out source. For core entries outside the current section, select the listed skill names and use the same command as other entries. Use project scope and copies. For example, `npx --yes skills@1.9.0 add ./source --agent codex --skill grilling --copy --yes` writes `.agents/skills/grilling` in the staging project. The package cache can be inside the staging project when needed. The staging project owns its temporary lockfile.
4. For each selected skill directory reported by the installer, run `LVR booster deploy --name <id> --harness <harness> --sha <sha> --from .lvr/booster-stage.<id> --path <native-relative-skill-path> --section <S>`. It places the copy in the actual project and records its version and path. For bootstrap, omit `--section`. A result of `already-present` means the user owns that copy. During a retry, inspect the relevant paths and journal first, and use a fresh stage if needed.
5. Confirm that the selected harness lists or can load the skill from the actual project. Load it before running the section's procedure. If the installer, deployment, or load check fails, mark the entry failed or degraded as appropriate and ask once in User Language whether to help install it, continue degraded, or stop. Continue degraded records the choice in the journal and Section Record, and S9 shows it in OVERVIEW. Stop preserves the current checkpoint. Remove only the disposable stage you created after deployment is accounted for.

Playwright and Firecrawl are optional MCP services. Before adding or changing one, get explicit approval for the service and its project scope. Check whether the user already configured it. For a new configuration, record `booster_installed` with `kind: "mcp"` and `consent: true` plus the exact scope and path. Clean up such a configuration only through a separate approved, provider-specific operation. Keep user or shared configuration intact.

## End of the pipeline or a later run

1. **Initial run.** Handoff owns cleanup after `handoff_done` unless the owner chose `/lvr-build` next. Record `cleanup_owner: "handoff"` or `"build"` on `handoff_done`. For a planned Recipe build, keep tracked copies through build verification. `/lvr-build` then owns cleanup after `build_done`. A paused or blocked build keeps its checkpoints and copies. If the owner closes the build instead, offer its pending cleanup.
2. **Later run.** Add-feature, review and brand plan their own applicable boosters, reuse working copies and stage missing aids just in time. After the run's closing checkpoint, scope cleanup to its opening and closing event sequences with `LVR booster cleanup --from-seq START --through-seq END`. An already installed copy belongs to its original window, even when the current run used it. On resume, inspect the run's journal window to continue from the first unclosed step. If a previous run completed but stopped before offering cleanup, `/lvr-continue` can take over its consent prompt. Use the saved `cleanup_owner` to keep copies for a pending build.
3. **Consent.** Use `LVR booster cleanup --through-seq END` for the initial pipeline and both sequence bounds for a later run. Ask once in User Language, “Remove these skill copies Recipe installed for this project?” List exact eligible paths. Record a declined path with `booster_choice` (`name` from the receipt, `choice: "keep"`, `path` and numeric `close_seq`). A retry with the same end checkpoint preserves that path.
4. **Approved paths.** Keep the same bounds and run `LVR booster cleanup --confirm --path PATH` separately for each exact approved path. The helper checks the managed receipt and current contents, writes `booster_uninstalled`, and prunes only Recipe-created empty parents. `state.boosters.installed` reflects the result. Copies that are modified, absent, untracked, user-owned or outside the window stay in place.
5. If cleanup reports a journal or state error, follow `/lvr-continue`. A `.lvr/booster-remove.*` directory from an interrupted move can contain a preserved copy. Keep it until the journal and receipt for that exact path have been reconciled.

Without Node, use the same staging, exact-path checks and journal events. Keep ownership evidence for every new copy. Only remove a copy after approval and a comparison to that evidence. If identity, ownership or contents are uncertain, keep the copy and report its path.
